# Writing Style Guide

このドキュメントは、プロジェクトにおける文章作成ルールをまとめたものです。
実際の ComfyUI 解説記事の文体・構造・語り口を忠実に再現し、読みやすく統一されたドキュメントを維持することを目的とします。

## 01. 基本方針

- **自然な日本語**: 翻訳調を避け、やわらかく、日常的に読める日本語を書く。
- **必要十分・シンプル**: 解説は最短で役割が分かるように始め、不要に長文化しない。
- **英語用語は原則そのまま**: `Workflow` / `Checkpoint` / `string` / `widget` など、ComfyUI やプログラミングで一般的な語は英語を優先する。必要に応じてカタカナ補足を添えてよい（例: `string`（ストリング））。
- **やわらかい技術文書**: アカデミックではなく、読者に語りかけるような文体を維持する。
  - 例: 「〜なんですね」「〜といった具合です」「〜することができます」
- **著者の視点・軽い評価を許容**: 「これはあまり使われません」「個人的にはこちらを推奨」など、適度に判断を述べてよい。

## 02. 文体

- **敬体（です・ます）** を基本とする。
- 手順や UI 操作は **体言止め** を使い、短くまとめる。
  - 例: 「〜をクリック」「〜を選択」
- 読者がつまづきやすい箇所では、さりげなくフォローする。
  - 例: 「どれを選んでもOKです」「地味ですが重要です」
- 冗長なラベル（例: 「操作：」「注意：」）は使わず、自然な流れで説明する。

## 03. ページ構成ルール

実際のあなたの記事の構造を基準とする。

### 3-1. 見出し構成

- **H2 (`##`)**：大カテゴリ（例: マスクの作成 / マスクの編集 / ノードの追加）
- **H3 (`###`)**：ノード名・操作名、その他
  - 例: `### GrowMask ノード`
- 各項目は「1 ノード 1 見出し」を基本とする。
- **H4 以下は使用しない**。必要なら箇条書きで代替する。

### 3-2. セクション境界

- テーマが大きく変わる箇所では `---` を入れて区切る（あなたの既存記事の慣例に合わせる）。

## 04. 各項目（ノード解説）のテンプレート

あなたの文章パターンを標準化すると以下になる。

```markdown
### ノード名

![](URL){media=image}

[](/workflows/...json)

一文で役割を説明する。

必要なら、パラメータや使いどころを箇条書きで補足する。
- ...
- ...

場合によっては短い Tip・注意書きを追加してもよい。
```

### 4-2. mediaRow の補足（画像の下にリンクを置きたい場合）

`mediaRow` の本文内で、画像の下にリンクや短い補足を置きたい場合は `mediaFooter` を使う。

```markdown
{% mediaRow img="..." width=50 align="left" %}
本文...

{% mediaFooter %}
[](/workflows/...json)
短い補足文もOK。
{% endmediaFooter %}
{% endmediaRow %}
```

`mediaFooter` は **画像の下** に表示される。本文とは別枠になるため、右側が窮屈なときの退避先として使える。

**特徴として重要なルール：**

- **最初の一文で役割を言い切る**（あなたの文体の最大の特色）
- **画像 → workflow → 説明** という「固定の並び」を守る
- 説明文は冗長にせず、1〜3文で完結させる
- 実務的な使いどころは柔らかく補足する
  - 例: 「全面を塗りつぶしたマスクが必要な場合に使用します」

## 05. リスト（箇条書き）

- 通常の箇条書きは **ハイフン `-`** を使う。
- 手順として番号そのものに意味がある場合は、Markdown の ordered list（`1.` `2.`）を使ってよい。
- 既存記事にある `- 1.` `- 2.` は「手書き番号つきの通常箇条書き」として扱い、必要がなければ無理に書き換えない。
- 入れ子は **スペース 2 つ** でインデント。
- 説明の粒度は短く、1文を長くしない。

例：

```markdown
1. ノードを選択
2. `Node Selection Toolbox` の `🕸️` をクリック
```

## 06. コードブロック

- リスト内に含める場合はインデントを揃える。
- コード以外（文章）の囲いにコードブロックを使わない。

## 07. 用語の統一

- **workflow**：小文字で統一。
- **ComfyUI**：正式表記 ComfyUI。
- 日本語本文中の英字語・製品名・UI 名の前後には、原則として半角スペースを入れる。
  - 例: `ComfyUI で生成する` / `LoRA を学習する` / `Batch Size を上げる`
  - ただし、句読点・括弧・行頭・行末では不要。
- 型・パラメータ・ノード名は backtick で囲む。
  - 例: `MASK` / `IMAGE` / `delimiter` / `String (Multiline)`。

## 08. 画像・動画

`{media=...}` は表示方法の指定で、R2（`/media/...`）/ Gyazo どちらでも同じように使う。

- ノードの静止画 → `{media=image}`
- UI 操作・アニメーション → `{media=loop}`
- プレイヤー再生 → `{media=player}`
- 既存の `{gyazo=...}` は同じ意味の互換記法。新規では使わない。
- R2 の画像は `/media/<論理名>` で参照する。論理名は原本置き場（`COMFY_MEDIA_ORIGINALS`）からの相対パス（例: `basic-workflows/minimax-h3/minimax_h3_audio_driven_i2va.png`）。
- 新しい画像は原本置き場に置き、`npm run media:put -- basic-workflows/minimax-h3/minimax_h3_audio_driven_i2va.png` を実行して、出力された Markdown を貼る（原寸 WebP への変換・R2 アップロード・`src/_data/media.json` 登録まで自動。サムネイル・記事用・OGP 用のサイズは配信時に自動生成される）。原本 PNG は原本置き場にだけ置き、R2 には上げない。
- `media.comfyui.nomadoor.net/...` の物理 URL は記事に直接書かない（`check:media` でエラー）。
- 原本は `<セクション>/<記事 slug>/<ファイル名>` に置く（workflow JSON と同じ構成）。フォルダは既存の記事 slug をそのまま使う。
- ファイル名は小文字 snake_case で、単体で何の画像か分かる名前にする（例: `minimax_h3_audio_driven_i2va.png`。`audio_driven_i2va.png` まで短くしない）。記事タイトルや本文では正式表記（`MiniMax H3` など）を使う。
- 公開後の論理名は安定 ID として扱い、安易に変えない。
- 動画など重いメディアは Gyazo を使ってもよい（URL を直接書く）。

テンプレ：

```markdown
![](/media/basic-workflows/minimax-h3/minimax_h3_audio_driven_i2va.png){media=image}
![](https://gyazo.com/<id>){media=loop}
```

## 09. Tip・補足・注意書き

- 必要な場合は `blockquote` (`>`) を使用。
- トーンはやわらかく断定しすぎない。

例：

> 実際のところ、ミュートはあまり使われません。

## 10. 著者性と編集方針

- 著者は人間オーナーであり、エージェント（AI）は大幅な改変を行わず編集・改善に徹する。
- エージェントが行うのは以下：
  - 誤情報の修正
  - 読みやすい構造への調整
  - 不足している説明の補完提案
  - 用語統一・スタイル統一

## 11. Frontmatter Dates

- 記事ページには、分かる範囲で `created` と `updated` を付ける。
- `created` は、そのページを最初に公開・作成した日付を表す。
- `updated` は、読者に意味のある本文・構成・データの更新日を表す。
- 表記は `YYYY-MM-DD` に統一する。
- 翻訳ページは、原則として対応する日本語ページと同じ `created` / `updated` を使う。翻訳だけを後から大きく直した場合は、その言語ページの `updated` を更新してよい。
- 日付が推測できない場合は無理に補わず、分かるページから段階的に追加する。

## 12. ZH 翻訳ルール（下地 / 参照あり）

参照: https://docs.comfy.org/zh-CN（ComfyUI 公式の中文表記・用語感）

### 12-1. 基本方針
- **簡体中文（zh-CN）を基準**にする。
- 中国本土/台湾どちらでも不自然にならない **中立的な表現** を選ぶ。
  - 地域スラングや俗語は避ける。
  - 「术语は英語 + 中文補足（初出のみ）」を許容する。
- 日本語記事の **やわらかく丁寧な口調** に合わせる（短文・過度に硬くしない）。

### 12-2. 用語ルール（例）
- **ノード名 / UIラベル / モデル名 / ファイル名 / コード / パラメータ名** は英語のまま。
- `backtick` で囲まれた語は **原則そのまま**。
- 一般語は中国語に寄せる（例: workflow → 工作流 / node → 节点 / model → 模型）。
- workflow の本文表記は **工作流** に統一（初出のみ “workflow（工作流）” 併記可）。
- 公式表記に合わせる（用語の語感は docs.comfy.org/zh-CN を優先）。
- 参考用語（初出のみ英語補足OK）:
  - 工作流（workflow）
  - 节点（node）
  - 模型（model）
  - 提示词（prompt）
  - 种子（seed）
  - 采样（sampling）
  - 队列（queue）

### 12-3. 翻訳範囲
- 翻訳対象: 本文、見出し、要約。
- 固定: `slug` / `navId` / `section` / `permalink`（変更しない）。

### 12-4. 記法
- 記号は日本語版と同じルール（`-` 箇条書き / H2・H3のみ）。
- 機能名は **英語を残しつつ中文で補足** する（初出のみ）。

### 12-5. 原文尊重（JAソース準拠）
- **日本語原稿の表現は、意味が通る限り無断で正規化しない**（例: くだけた口調、記号、軽いニュアンス）。
- エージェントは「読みやすさ」を理由に、原文の語感・温度感を勝手に翻案しない。
- 引用・参照・注釈の文言は、原文由来であることを優先して保持する。
- 変更対象は、原則として **事実誤り / リンク切れ / 明確な誤字脱字 / ビルド不整合** に限定する。
