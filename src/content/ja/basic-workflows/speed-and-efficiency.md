## 高速化と軽量化とは？

Stable Diffusion 1.5 は登場当初、推奨 VRAM が 10GB 程度とされ、RTX 3080 クラスで 1 枚生成するのに 5 秒前後かかる、というベンチマーク結果が多く報告されていました。  
それも今や昔。技術の進歩により、現在では CPU のみで数秒〜十数秒程度で推論できたり、1 秒間に何十枚も画像を生成できるようになってきました。

拡散モデルの歴史は、ある意味では **「高速化と軽量化の歴史」** と言ってしまっても良いでしょう。

ここで注意したいのは、次の 2 つは似ているようで別物だということです。

- **高速化：同じハードウェアで、1 枚あたりの生成時間を短くする**
- **軽量化：同じモデルを、より少ない VRAM・メモリで動かせるようにする**

軽量化のための技術（量子化 / GGUF など）を使うと、VRAM は削減できても、場合によっては推論速度がむしろ低下することもあります。

このページでは、 軽量化を「GPU での計算量削減および VRAM 使用量削減」 として扱い、目的に応じてどういう技術を使い分けるべきかを整理していきます。

---

## どれを使うべきざっくりまとめ

このページでは、次のような「何を優先したいか」の切り口で話を整理します。

- とにかく速くしたい  
  - サンプリングステップを減らす「蒸留」
  - Attention の実装を工夫する「Attention 最適化」
  - サンプリングの中身を賢くスキップする「キャッシュ」

- VRAM を削りたい / 動くだけで良い  
  - モデルの重みを小さくする「量子化」
  - モデルの一部を CPU に逃がす「オフロード / Block Swap」
  - 画像や動画を分割して処理する「タイル化」

## 高速化・軽量化技術の一覧

ここでは、よく名前が挙がる高速化・軽量化技術をざっくり一覧にしておきます。  
「導入のしやすさ」は、セットアップの難しさと、既存 workflow に組み込みやすいかどうかの目安です。

> あくまで「ざっくりした地図」なので、環境やモデルによって評価が逆転することもあります。  

| 手法名           | タイプ                         | 高速化 | 軽量化                             | 導入のしやすさ |
|------------------|--------------------------------|--------|------------------------------------|----------------|
| 8-bit 量子化     | モデルの量子化                 | △〜○   | ○（VRAM 約半減）                  | 中             |
| 4-bit 量子化     | モデルの量子化                 | △      | ◎（VRAM 大幅削減）                | 中             |
| GGUF             | モデル圧縮・専用フォーマット   | △      | ◎（モデル容量・VRAM 削減）        | 低             |
| 蒸留             | モデル蒸留（Lightning / schnell 等） | ◎ | ―（モデルサイズはほぼ同じ）       | 中             |
| Attention 最適化 | Attention 実装の置き換え       | ○      | ―                                  | 低〜中         |
| サンプリングキャッシュ | サンプリングのキャッシュ   | ○      | ―                                  | 低             |
| 小型VAE          | VAE の小型版への置き換え       | ○〜◎   | ○（VAE の計算負荷削減）           | 高             |
| CPUオフロード    | モデルの一部を CPU に退避      | ✕      | ◎（VRAM を数 GB まで削減可能）    | 中             |
| Block Swap       | Transformer ブロック単位の退避 | ✕      | ◎                                  | 低〜中         |
| VAEタイル化      | 画像をタイル状に分割して処理   | ―      | ○（大画像生成時の VRAM 節約）     | 中〜高         |

## 量子化（8/4bit, GGUF）

量子化は、**モデルの重みを低精度化して、VRAM やメモリ帯域を削減する**手法です。  
FP16 で持っていた重みを INT8 / INT4 に落とし込むことで、メモリ使用量を減らします。

- 8-bit 量子化  
  - モデルに`fp8`とつい￥
  - VRAM 使用量をざっくり半分程度に抑えられるます。
  - うまく量子化できれば、品質劣化はほとんど気にならない場合もあります。
  - GPU によっては INT8 計算が高速化されており、速度がほぼ変わらない、あるいはわずかに向上することもあります。

- 4-bit 量子化  
  - VRAM 削減効果は非常に大きい一方で、  
    - 重みの再構成にオーバーヘッドがかかったり  
    - 画質の劣化が見える形で出てきたり  
    することがあります。
  - LLM では 4bit 量子化が広く使われていますが、拡散モデルではまだ「実験中」といった印象が強いです。

- GGUF  
  - 量子化された重みを格納するためのフォーマット（元々は LLM 用）です。
  - ComfyUI では、特定のモデル（Flux 系など）を GGUF で読み込むノードもあります。
  - CPU や低 VRAM 環境で「とりあえず動かす」用途には向きますが、セットアップの手間や対応モデルの少なさを考えると、現時点では導入ハードルは高めです。

## 蒸留（Lightning / schnell など）

蒸留は、**大きな教師モデルの振る舞いを、小さな（あるいはステップ数の少ない）モデルに真似させる**手法です。  
拡散モデルでは特に、「サンプリングステップ数を減らしても品質を維持する」ことを狙って使われます。

代表例としては次のようなものがあります。

- SDXL-Lightning 系  
  - SDXL を 4 / 8 ステップで回せるように蒸留した LoRA / モデル群です。
  - LoRA とサンプラー設定を切り替えるだけで、通常の SDXL より大幅に高速化できます。

- FLUX.1-schnell  
  - FLUX.1 の低遅延版で、少ないステップ数での生成を前提に調整されています。
  - 通常版より、「速さ」に振った設定だと考えると分かりやすいです。

蒸留モデル全般に共通するポイントは次のようなものです。

- サンプリングステップ数を減らせるので、1 枚あたりの生成時間が大幅に短くなる。
- モデルサイズ自体は元のモデルと大きくは変わらないため、VRAM 的にはそれほど軽くなりません。
- ごく一部のプロンプトや難しいシーンでは、オリジナルより弱い部分が出ることもあります。

つまり、蒸留は「VRAM はそのままに、時間だけ削る」タイプの高速化手法だと考えると整理しやすいです。

## Attention 最適化（FlashAttention / SageAttention など）

拡散モデルや Transformer モデルでは、Self-Attention の計算がボトルネックになりやすいです。  
そこで、Attention 部分だけを高速な実装に差し替える手法がいくつか提案されています。

代表的なものとしては次のようなものがあります。

- FlashAttention 系  
  - メモリアクセスを最適化した Attention 実装です。
  - PyTorch 2 系の `scaled_dot_product_attention` や、一部の diffusers 実装でも利用されています。

- SageAttention / Nunchack などの専用実装  
  - Attention テンソルを内部的に量子化したり、演算順序を工夫することで高速化を狙う実装です。
  - 既存の FlashAttention2 や xFormers と比較して、さらに高速な結果が報告されているものもあります。

注意点として、SageAttention や Nunchack のような実装は、

- 専用のビルドやライブラリの導入が必要
- ComfyUI では専用ノードや特定の custom node パックが必要な場合が多い
- 既存の workflow にそのまま差し替えるのが難しい

といった事情があります。

このサイトでは、**「一通りのセットアップを済ませた上級者が、自力で試行錯誤している領域」**と位置づけており、あえて詳しい導入手順やノードの使い方は扱わない方針にしています。  
「こういう方向性の高速化手段がある」ということだけ、ここで軽く触れておきます。

## サンプリングキャッシュ（TeaCache）

TeaCache は、主に DiT 系の拡散モデル向けに提案されている「サンプリング過程のキャッシュ手法」です。

- 連続するサンプリングステップのうち、「ほとんど変化しない」部分の出力をキャッシュしておき
- 変化が小さいと推定されるステップでは、前のステップの結果を再利用して計算をスキップする

という発想で、高速化を狙います。

特徴としては次のような点があります。

- モデル自体はそのまま使えます。追加学習や蒸留は不要です。
- キャッシュの強さを調整することで、「品質 vs 速度」のバランスをユーザー側で決められます。
- 現時点では DiT 系モデル（Flux / SD3 系など）と相性がよく、UNet 系では適用範囲が限られています。

「蒸留」はモデルそのものを作り替えてステップ数を減らす手法で、  
「TeaCache」は同じステップ数のまま、中で「サボれるところ」を見つけて高速化する手法、という感じで分けて考えると分かりやすいです。

## 小型VAE

VAE（Variational AutoEncoder）は、画像と潜在表現を相互に変換する部分です。  
高解像度での decode や、動画生成のように大量のフレームを連続して扱う場合、VAE がボトルネックになることがあります。

小型 VAE（例：TAESD 系）は、元の VAE を蒸留・圧縮したもので、次のような特徴があります。

- 元の VAE とほぼ互換の latent 表現を扱えるように設計されている
- decode が非常に速く、リアルタイムプレビューや中間チェックに向く
- 細かいテクスチャや色味については、オリジナルの VAE よりわずかに弱くなることが多い

実務的な使い方としては、

- 普段のプレビューや中間レンダリングは小型 VAE で回し
- 最終書き出しだけオリジナル VAE で decode し直す

といった「二段構え」にするパターンが多いです。  
生成そのものの計算量は変わりませんが、「画像が見えるまでの時間」を体感的にかなり短くできます。

## CPUオフロードと Block Swap

VRAM が明らかに足りない場合、**一部の重みや中間テンソルを CPU 側メモリに逃がす**ことで、なんとかモデルを動かす手段があります。

代表的なものは次の 2 つです。

- CPUオフロード  
  - Text Encoder や VAE の一部など、あまり頻繁に使わない部分を CPU に退避します。
  - VRAM のピーク使用量は大幅に下がりますが、その部分を呼び出すたびに PCIe 経由でデータ転送が走るため、生成速度は確実に低下します。
  - 「遅くても良いので、とにかく動かしたい」というときの最後の手段です。

- Block Swap  
  - Transformer をブロック単位に分割し、必要なブロックだけ GPU に載せる手法です。
  - 使っていないブロックは CPU メモリに退避しておくことで、巨大なモデルでも VRAM に載せやすくします。
  - 特に動画生成系の大型モデル（WanVideo 系や LTX 系）では、Block Swap を前提にした設計のものも出てきています。

どちらも「高速化」ではなく、**「VRAM を犠牲にするか、時間を犠牲にするか」のトレードオフを後者に振る手段**です。  
時間をかけてでも回したい workflow のための技術として覚えておくとよいでしょう。

## VAEタイル化（Tiled VAE / Temporal Tiling）

大きな解像度の画像や、長尺の動画を扱うときには、**空間や時間を小さなブロックに分けて処理する**という発想もよく使われます。

- VAEタイル化（Tiled VAE）  
  - 画像をタイル状に分割し、タイルごとに encode / decode を行います。
  - タイルの境界は少し重ねて処理し、あとで繋ぎ直すことで継ぎ目を抑えます。
  - 一度に扱うピクセル数が減るため、超高解像度でも VRAM のピークを抑えられます。

- Temporal Tiling（時間方向のタイル化）  
  - 動画生成モデルでは、時間軸を数フレーム単位の塊に分けて処理する手法も広く使われています。
  - 長尺動画でも、一定の VRAM 内に収めながら順次生成していくことができます。

これらは「速くする」ための技術というよりも、**「本来ならメモリ的に無理なサイズを、なんとか扱えるようにする」ための技術**です。  
超高解像度や長尺動画に挑戦したくなったときに、思い出してもらえると良いと思います。
